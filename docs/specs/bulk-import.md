# Bulk product import

Phase 2 (PLAN.md section 5). A manager or owner uploads an Excel, CSV or JSON file of products; a background job creates or updates them in batches; the import can be undone for 24 hours.

## Decisions (defaults, 2026-10-10; change on request)

- **Scope:** products and variants, with category (by name, created if missing), cost, VAT category and opening stock. **Stock levels and customers use the same pipeline** (upload, mapping, preview, background job `import-products`, progress, 24 h undo; `import_jobs.type` is `products`, `stock` or `customers`, chosen on the first screen or with `?type=`). **Suppliers are NOT built**: there is no suppliers feature or table in Tillflow yet (PLAN.md lists suppliers and purchase orders as v2), so there is nothing to import into; a suppliers import needs that feature first.
- **Stock import:** one row per SKU or barcode with a whole-number quantity (0 to 1,000,000) and an optional note. Mode `count` = the number is what is on the shelf (writes the difference, reason `count`; an equal count is skipped); `received` = a delivery, added to stock (reason `received`, at least 1). Same ledger and reasons as the manual stock screen, so reports are unchanged. Only stock-tracked, non-archived products of this shop match; an unknown SKU/barcode is a problem row at the check step. Undo adds the opposite `adjustment` per change (history is kept; it can drive stock negative if the product sold since).
- **Customer import:** name (required), email, phone, VAT number, address, notes, checked by the same rules as the customers screen (`app.clean_customer`). Matched by email (case-insensitive, among non-erased customers); create-only skips an existing email, update changes the name and only the other fields the file gave. **Marketing consent is never imported**: it needs an explicit tick per customer on the customer page. A repeated email in the file: the first row wins. Problem rows name the row and field only, never the value. The uploaded file holds personal data and is deleted after 7 days (or by the next upload); nothing from it is logged. Undo anonymises customers the import created (the row stays, as the erase button does) and restores the ones it updated.
- **Server-side parsing only** (`src/lib/import/parse.ts`): CSV (Papa Parse), `.xlsx` (ExcelJS, first sheet; a formula's stored result is read, never evaluated), JSON (an array, or `{ "products": [] }`). Limits: 10 MB, 50,000 rows, 60 columns. The extension decides the format and the content must agree (`.xlsx` must be a zip, text files must not contain NUL bytes).
- **`.sql` is never accepted or run.** The upload answers with a plain explanation of how to export CSV or Excel. Imports are parsed, never executed (CLAUDE.md rule).
- **One validator.** Each row becomes a `RawProduct` and goes through `parseProductForm` (`src/lib/catalog-schema.ts`), so the import and the product form cannot disagree (prices via `parseCents`, barcode shape, per-type attributes, barcode/SKU only for types that use them). The preview and the job use the same code; the job validates again and trusts nothing from the browser.
- **Bad rows never stop the import.** They are listed (first 100 on screen, the full list as a CSV rebuilt from the stored file) and skipped. Repeated SKU or barcode inside the file: the first row wins. A barcode or SKU that belongs to another product in the shop fails that product only (each product runs in its own sub-transaction in `ops.import_apply_batch`).
- **Create-only or create-and-update**, matched on SKU or barcode. A row without the match value is always created. An update changes only what the file gave: name and price always; SKU, barcode, cost, category, VAT (and take-away VAT), track-stock and each attribute (age restriction, deposit, brand...) only when that cell has a value, so a partial spreadsheet never resets a product's VAT or attributes to defaults. It never changes stock; opening stock applies to new variants only.
- **Clothing:** rows with the same style code (or name) and VAT category become one product with size/colour variants. A repeated size and colour keeps the first row.
- **VAT column:** a category name (`STANDARD`, `CATERING`...) or a percentage (23, 13.5, 9, 0, 4.8). `9` is `CATERING` in a café or restaurant and `SECOND_REDUCED` elsewhere. Blank uses the type's default and is counted on the check screen. Hot take-away and similar rulings are the shop's/accountant's choice, as in the product form.
- **Presets and auto-match:** Square, Lightspeed, Imonggo and Shopify column names (`src/lib/import/presets.ts`) plus header-name synonyms. The vendor column names follow their documented exports and have NOT been checked against live exports; the mapping screen always shows the result for the shop to correct. Saved mappings are per shop (`import_mappings`).
- **Files** are stored in Postgres (`import_files`, bytea) behind `src/lib/storage` so no new service or secret is needed, and deleted after 7 days by the hourly `import-purge` job. Switching to object storage means changing `src/lib/storage` only.
- **Job:** pg-boss `import-products`, batches of 500, no automatic retry (a failed import is marked failed and re-uploaded; a re-run is still safe because ids are derived from the import id and row, and the database remembers what the import did in `import_changes`). Progress is in `import_jobs.processed_rows`.
- **Undo (24 h):** `public.undo_import` archives what the import created (SKU and barcode freed, cost removed, opening stock reversed with an `adjustment` row), restores what it updated (including cost and the product's fields), and never deletes. A change that cannot be put back (its SKU was taken since) is left and counted as "kept". Categories created by an import stay.
- **Roles and limits:** owner/manager only; 5 uploads per hour per shop (`import` bucket, route); one queued/running import per shop (one stuck for over 2 hours is marked failed by the next upload); a new upload replaces one never started; only the newest 10 stored files per shop are kept (the oldest file is dropped, so the 7-day copy of an old import may go earlier; also enforced against direct API calls). Only the manager who uploaded can confirm. A second Start does nothing.
- **Canonical xlsx (`src/lib/import/xlsx-zip.mjs`):** ExcelJS never receives the uploaded bytes. The upload is read once with strict rules (single-disk archive, directory contiguous with the end record, every header inspected and equal in number to the declared count, no encryption, plain safe names, no duplicates, local and central names equal, no overlapping entries), only a whitelist of spreadsheet parts is kept (workbook, sheetN.xml sheets, shared strings, styles, theme, document properties, and the sheet relationships, drawings, tables and comments that ExcelJS fails without, using exactly the file names ExcelJS itself loads; images, macros, embedded files, external links and custom XML are dropped), each kept part is inflated under its own cap (32 MB per sheet and for the shared strings, 8 MB styles, 4 MB the rest, 64 MB in total; a larger sheet is refused as too big, split the file) and checked against its CRC and size, and a fresh stored zip is written for ExcelJS. The older early check stays in front as a cheap refusal. This removes the class of "the guard and JSZip read the zip differently" bugs instead of chasing them one at a time; it is defence in depth, not a replacement for process isolation (Layer 2): it bounds the zip, not what ExcelJS builds from the XML (a tiny sheet with a `mergeCell` ref of A1:AZ100000 or a `col` range of millions makes ExcelJS allocate gigabytes), which only a memory and time limit on the parser process can bound.
- **Excel (.xlsx) is parsed in a separate, restricted process, and is OFF by default** (exception, decided 2026-10-13 so the owner can test with real files: ON by default on STAGING only, i.e. when `NEXT_PUBLIC_APP_ENV=staging` and `IMPORT_XLSX_ENABLED` is unset; `IMPORT_XLSX_ENABLED=false` forces it off there; production and local stay off unless `=true`; the per-process self-test must still pass; the Hostinger probe has still NOT been run) (`src/lib/import/sandbox/`). ExcelJS never parses an upload inside the web server process (the Excel template download still uses it to WRITE a fixed file, which is not parsing), and there is deliberately **no in-process fallback**: when Excel is off or the host cannot run the sandbox, an `.xlsx` is refused with a clear message (save as CSV) and CSV/JSON keep working under their normal validation, authorization and rate limits.
  - **Switch:** `IMPORT_XLSX_ENABLED=true` (exactly that string; anything else is off). Even then it only runs after a self-test on that host passes. The self-test checks: the parser files exist; reads outside the allow-list, writes, child processes and workers are denied; no secret-looking environment variable reaches the child; a runaway child is stopped by the time limit and is gone afterwards; on Linux the child's resident memory can be read (otherwise its ceiling would silently do nothing); and the real parser reads a built-in workbook under all of that. It does NOT check the heap cap, the output cap or the `ulimit` limits: only the manual probe does. If a check fails the state is `unavailable` (checked again after a minute). `/api/health` shows `importXlsx`: `disabled`, `unchecked`, `ready` or `unavailable`, per app process. Nothing is started while it is off.
  - **What the child gets:** Node's stable permission model (`--permission`, Node 22.13+; the older experimental flag is not accepted): no file writes, file reads only from `src/lib/import` and `node_modules`, no child processes, no worker threads; an empty environment (no database URL, keys or session); a V8 heap cap (`--max-old-space-size`, default 256 MB).
  - **What the parent enforces (SIGKILL):** a wall-clock timeout (20 s); a resident-memory ceiling (768 MB), polled every 50 ms from `/proc` on Linux only, so a child can overshoot it between polls (in tests it stopped within 2 to 9 MB of a 256 MB ceiling, but that is not a guarantee); and an output ceiling (40 MB). On Linux with `/bin/sh` the child also starts under a CPU-time limit (`ulimit -t`, timeout + 5 s) that ends it even if the parent is gone, and, if `IMPORT_SANDBOX_ULIMIT_KB` is set, an address-space ceiling (`ulimit -v`, off by default, needs about 2 GB to leave Node room to start). The wrapper fails closed: a limit that cannot be applied makes the child exit with 97, which the app treats as "this host is unavailable". Every live child is killed when the app process exits normally; a hard kill of the app is covered only by the CPU-time limit. A child that crashes, hits V8's heap abort or is killed is a normal refusal ("too large or complex"), never an error in the web server.
  - **Boundary:** the file goes to the child on stdin; the child writes one JSON line; the parent accepts only an exact Zod shape (headers and rows of strings, at most 61 columns and 50,000 rows, cells at most 32,767 characters, no extra keys, rows as wide as the header) and then validates the rows like any other upload, before `buildItems` and the existing RLS-checked writes. The authorization check (`authorizeApi`, RLS-scoped lookups) comes first in every route; uploads are limited to 5 per shop per hour and preview/problem-file requests, which re-read the stored file and so start a parser, to 60 per shop per hour (`import-reparse`). The child has no database, session or identity.
  - **Concurrency:** at most 2 parses at once per app process and 4 waiting (10 s); more is refused as "busy". The self-test and probe children are outside this limit (at most two more, briefly), so size the memory budget as (2 + 2) children plus the web server. The limit is per process, and one tenant's requests share it with everyone else's (the per-shop rate limits above bound how much of it one shop can use).
  - **Limits via the environment** (positive integers, otherwise the defaults): `IMPORT_SANDBOX_TIMEOUT_MS`, `_HEAP_MB`, `_RSS_MB`, `_OUTPUT_BYTES`, `_ULIMIT_KB`, `_CONCURRENCY`, `_QUEUE`, `_QUEUE_WAIT_MS`.
  - **Not enforced, by design of Node:** network access. Node 24's permission model has no switch for it, so a child can still reach the network (localhost and internal services included) and it holds the uploaded file; it has no credentials, database or session to use, but a code-execution flaw in ExcelJS would not be contained against the network. Keep Node on a current security release (the permission model has had bypass fixes). On Windows the resident-memory and CPU-time ceilings do not exist (they need `/proc` and `ulimit`).
  - **The probe** (`src/lib/import/sandbox/probe.mjs`, run by hand as `node src/lib/import/sandbox/probe.mjs` or at boot with `IMPORT_SANDBOX_PROBE_ON_BOOT=true`, which logs one JSON report) makes a misbehaving child try every forbidden thing and reports what the host ACTUALLY enforced. It must say `isolation-enforced` on the real host before `IMPORT_XLSX_ENABLED` is turned on there. It never lets a child pass about 900 MB. **Evidence so far** comes from a developer Windows machine and Linux containers (Node 24, non-root, 1 to 4 GB memory limit, 256 processes, both npm and pnpm layouts) and NOT from Hostinger: on Linux every required control held (denied reads/writes/processes/workers, empty environment, heap abort contained, timeout kill, output kill, resident-memory kill within 2 to 9 MB of a 256 MB ceiling, CPU-time kill at 2 s, `ulimit -v` stopping an allocation near 750 MB, and the 2.6 KB `mergeCell` bomb ending only the child after about 3 s at 330 to 420 MB); and a child spinning at the time its parent exited was gone with the exit hook and orphaned without it. On Windows the memory and CPU-time ceilings were absent, as expected.
- **Abuse limits:** (zip-level limits are in the canonical xlsx bullet above and the isolation bullet below) JSON with more than 60 distinct keys is refused before any row is built; the mapping is limited to 8 KB; a column named like an Object method (`constructor`) is not read.
- **Audit:** `import.uploaded`, `import.confirmed`, `import.finished` / `import.failed`, `import.undone` in `audit_log` (ids and counts only, never product data).

## Known limits

- No suppliers import (no suppliers feature exists yet) and no SQL-dump parsing (a later version could parse `INSERT` rows into the same mapping screen without executing them).
- The 10 MB file is sent to Postgres as hex (about 20 MB request) through the Supabase API; if that limit bites, move `src/lib/storage` to object storage.
- No antivirus scan (PLAN.md says "scanned"): files are only parsed, never executed. CSV and JSON are still parsed in the app process (Papa Parse on at most 10 MB, `JSON.parse` after the key-count check); only Excel is isolated. The child's network access is not restricted (Node cannot), and nothing has yet been verified on the real Hostinger host: Excel stays off until the probe and the staging checks there pass. Real Excel, LibreOffice and Google Sheets exports have not been tested (no genuine files yet; `tests/fixtures/xlsx-real`). A legitimate sheet larger than 32 MB of XML is refused as too big (split the file).
- Undo restores the values from before the import even if someone edited the product since (it does not detect later edits), and archives created products even if they have been sold since. A failed import (partly written) can be undone for 24 hours too. Undo leaves the categories an import created, and for a clothing product the restored product fields come from the last variant restored.
- `ops.import_file` can read any import file by id for a running import: it is reachable only with the privileged job connection (as the other `ops` functions).
- Preview checks every row on each change of setting (a 50,000-row file takes a few seconds each time).
- Product images, modifiers groups, supplier and multi-location stock are not imported. Allergens use the 14 EU names (`cereals_gluten`, `milk`...), with `gluten`, `dairy`, `soy` and `tree nuts` accepted as aliases.
- The row numbers in errors are spreadsheet rows (header is row 1). For JSON they are the position in the array plus one.
- An import interrupted by a server restart stays "running" (and blocks new uploads) for up to 2 hours; then the next upload marks it failed (`stalled`). Whatever it had already written stays and can still not be undone (only `done` imports can be undone).
